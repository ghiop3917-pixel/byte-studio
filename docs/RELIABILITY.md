# Telegram-ядро, этап 1

## Порядок обработки

Рабочая точка входа — `python monitor.py`. Авторизация и JSON-настройки сохранены.

Оригинал, метаданные, задача обработки и позиция чтения записываются одной SQLite-транзакцией. Уникальная пара ID группы и сообщения предотвращает повторное создание исходной записи. Очередь сохраняет результат классификатора и создаёт лид с уведомлением другой транзакцией. Фильтрация применяется после сохранения оригинала.

Метаданные включают дату публикации и получения, автора, источник, ссылку, язык и статус. Язык определяется простым эвристическим правилом по алфавиту. Это не лингвистическая модель. Медиафайлы не скачиваются, сохраняются текст/подпись и тип вложения.

Позиции существующих источников сохраняются. Для нового источника первоначально загружаются последние 100 доступных сообщений, затем чтение продолжается по ID. Уже удалённые в Telegram сообщения и история до первоначальной границы не могут быть восстановлены программой.

## Очереди

`processing_queue` использует состояния `pending`, `processing`, `completed`, `failed`, `retry_wait`. Захват задачи выполняется в `BEGIN IMMEDIATE`, выдаётся уникальный токен и аренда на 120 секунд. Максимум пять попыток. Повторы назначаются через 30, 60, 120 и 240 секунд. Истёкшая аренда возвращает задачу в очередь, а исчерпавшая попытки задача получает `failed`.

`notification_queue` содержит полезную нагрузку, статус, число попыток, даты, ошибку и ID Telegram-сообщения при подтверждённой доставке. Внешняя отправка выполняется после завершения всех SQLite-транзакций.

Уникальность уведомления задаётся парой лида и получателя. Повторный анализ исходного сообщения не создаёт новый лид для того же получателя и не отправляет вторую карточку.

## Неоднозначная доставка

Bot API не предоставляет ключ идемпотентности для `sendMessage`. Exactly-once доставка не гарантируется.

После сетевого тайм-аута, ответа 5xx или прерывания процесса во время отправки уведомление получает `ambiguous`. Автоматического повтора нет, поскольку Telegram мог уже доставить сообщение. Лид и исходный текст остаются в SQLite.

Ответ 429 означает явный отказ по частоте. Он допускает ограниченный повтор с учётом `retry_after`. Постоянные ошибки 4xx получают `failed`.

Оператор проверяет чат перед ручной повторной отправкой. После ручного повтора остаётся риск дубля. В истории аудита фиксируется факт ручного решения.

## Источники и соединение

Каждая группа имеет собственное состояние в `source_health`. Обычные ошибки повторяются с увеличением задержки, после пяти последовательных ошибок источник получает `failed`. Остальные группы продолжают работать.

FloodWait сохраняет время следующей попытки и учитывается в числе последовательных неудач источника. Для общего ограничения метода устанавливается общий cooldown чтения истории или разрешения имён. После пяти неудач требуется ручное возобновление источника.

Соединение восстанавливается при следующем обращении. Попытки подключения Telethon ограничены. Сбой самого рабочего цикла завершает мониторинг с ошибкой, а состояние очередей сохраняется.

Процессы расширения списка групп и мониторинга могут влиять на общие лимиты одного Telegram-аккаунта. Это ограничение Telegram. Этап 1 не запускает дополнительные процессы поиска.

В одном процессе работают асинхронные циклы сбора, обработки, доставки, меню и контроля. Heartbeat сохраняется каждые пять секунд. Блокировка SQLite предотвращает одновременный запуск двух экземпляров `monitor.py`.

Автозапуск после перезагрузки ОС и сервис на VPS этим этапом не настраиваются.

## Контроль и восстановление

Для штатной остановки используй `python core_admin.py --stop`. Запрос проверяется каждые пять секунд. Прерванная отправка отмечается неоднозначной после истечения аренды. После остановки новый запуск выполняется обычной командой `python monitor.py`.

Состояние очередей, источников и heartbeat выводится командой

```powershell
python core_admin.py
```

Повторная классификация сохранённого сообщения по внутреннему ID

```powershell
python core_admin.py --reprocess 42
```

Ручная повторная постановка неоднозначного или неудачного уведомления

```powershell
python core_admin.py --retry-notification 12
```

Повторная проверка источника после устранения причины

```powershell
python core_admin.py --retry-source username
```

Очередь сохраняет получателя на момент получения сообщения. Смена получателя не перенаправляет уже накопленные сообщения автоматически. Выбранные направления читаются при обработке. После смены направления старые сообщения доступны для явной повторной обработки.

Отдельный `bot.py` сохранён для совместимости старого режима прямого Bot API. Долговечные очереди и контроль источников относятся к запуску через `monitor.py`. Одновременный запуск режима `bot.py`, меню и привязки получателя для одного токена конфликтует за получение обновлений. Повторную привязку следует выполнять при остановленном мониторинге.

## База и резервные копии

Таблицы `leads`, `delivered` и `cursors` сохраняются. Добавляются `raw_messages`, `processing_queue`, `lead_messages`, `notification_queue`, `source_health`, `core_events`, `core_heartbeat`, `core_locks`, `core_migrations`.

Перед первой миграцией создаётся копия через SQLite Backup API в `backups/`. Копия проходит `integrity_check`. Миграция аддитивная и выполняется одной транзакцией. Автоматическое удаление данных отсутствует.

Для отката остановить мониторинг и использовать проверенную копию базы вместе с кодом соответствующей версии. Новые сообщения, накопленные после копии, нужно предварительно сохранить отдельно. Копии содержат данные проекта и требуют защиты доступа.

## Проверки

Тесты запускаются командой `python -m unittest discover -s tests -v`.

Проверяются сохранность оригиналов, перезапуск, аренды, конкурирующие соединения, ограничение повторов, неоднозначная доставка, ответы 429, сохранение старых данных, независимость источников, FloodWait и обязательные примеры классификации.

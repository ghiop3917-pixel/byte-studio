# Архитектура

## Telegram-ядро

`monitor.py` использует сохранённую Telegram-сессию. `telegram_runtime.py` управляет сбором, обработкой, доставкой и heartbeat внутри одного процесса. `reliability.py` сохраняет оригиналы, позиции чтения, задачи и уведомления в monitor.sqlite3.

Сетевые отправки выполняются отдельно от транзакций. Неоднозначная доставка требует ручного решения. Подробности находятся в RELIABILITY.md.

## CRM-ядро

`crm.py` предоставляет сервис с проверкой владельца. Он работает с той же SQLite. `crm_migrations.py` добавляет версию 2, сохраняет старые ID и поля leads, связывает имеющиеся исходные сообщения и существовавшие черновики.

При создании нового Telegram-лида CRM-запись, клиент, источник, входящее сообщение, черновик и уведомление сохраняются в одной транзакции обработки. Повторная обработка не создаёт второй лид. Ручной импорт использует ключ платформы, источника и сообщения.

Денежные значения хранятся десятичными строками. Для них обязательна валюта. Пустые значения остаются NULL. Реальная выручка рассчитывается только по указанным владельцем суммам заключённых сделок, отдельно по валютам.

Объединение связывает карточки через merged_into. Исходные записи, отношения и история сохраняются на прежних ID. Основная карточка собирает записи участников группы. Отмена объединения восстанавливает предыдущие связи. Созданные после объединения записи относятся к карточке, на которой владелец их создал.

## Внутренний API

Этап 3 добавляет lead_analysis.py для объяснимой классификации, sales_drafts.py для локальных черновиков и quality.py для сохранения результатов, проверки и обратной связи. Миграция analysis_migrations.py имеет номер 3. Данные анализа сохраняются в той же транзакции обработки, что CRM-карточка и уведомление.

Сомнительные сообщения доступны через API и бот. Их ручное одобрение использует существующую долговечную очередь. Внешние языковые модели не подключены. Подробности и ограничения приведены в ANALYSIS.md.

`crm_api.py` слушает только 127.0.0.1. Требуются Bearer-токен из окружения и единственный владелец. Для изменяющих запросов нужен Idempotency-Key. Ответ изменения и его квитанция фиксируются одной транзакцией, повтор запроса возвращает прежний результат.

Внешние Origin и CORS сейчас закрыты. Подключение Netlify потребует отдельного этапа публичной защиты, HTTPS и настройки разрешённого frontend. API не отправляет сообщения клиентам.

`crm_export.py` создаёт CSV и XLSX. openpyxl уже установлен в рабочем окружении и используется только при экспорте XLSX. Формулы в пользовательском тексте нейтрализуются при экспорте. Новые AI-зависимости отсутствуют.

## Запуск

Мониторинг запускается через `python monitor.py`, локальный API — отдельной явной командой `python crm_api.py`. Каждый HTTP-запрос открывает своё соединение SQLite. Запись сериализуется транзакциями и busy_timeout. Для VPS 1 vCPU/2 GB нагрузку нужно измерить перед будущим развёртыванием. Автоматическое удаление и публичное развёртывание выключены.

## Продажи и веб-слой

`sales.py` готовит КП, вопросы и follow-up в существующих drafts. `sales_analysis.py` считает стоимость по вводным владельца и сохраняет ручной анализ ответа с черновиком следующего сообщения; стадия автоматически не меняется. `web/crm` — интерфейс на стандартном JavaScript без новых runtime-зависимостей. API обслуживает файлы только по явному списку путей, а не весь каталог проекта. Same-origin запросы локальной панели разрешены, внешние Origin закрыты.

`web_intake.py` принимает явную отправку формы, валидирует данные, согласие и honeypot; ограничение — пять новых заявок на идентификатор клиента за час. Заявка, клиент, запись журнала и outbox создаются атомарно. Повтор того же request_id возвращает квитанцию; изменённое содержимое с тем же ID отклоняется. IP не сохраняется в открытом виде, X-Forwarded-For не считается доверенным. Перед публичным запуском нужно спроектировать доверенный reverse proxy и защиту от распределённого спама.

`web/studio` — отдельный статический сайт и два интерактивных демо в памяти вкладки. Форма использует `/public/intake` на том же origin. Локально путь обслуживает API. На Netlify без отдельного backend отправка недоступна: интерфейс предлагает ручной Telegram-контакт. Публичное подключение backend и deployment пока не выполнены.

## Этап 7

insights.py строит отчёты по источникам и последним решениям владельца; quality_suggestions не меняют правила автоматически. maintenance.py выполняет ограниченные задания и проверенные SQLite-копии. operations_migrations.py — версия схемы 5. maintenance_loop в telegram_runtime.py использует один поток asyncio.to_thread и существующий процесс; сообщения Telegram он не отправляет.

web/crm/operations.js добавляет три панели без изменения публичного сайта. bot_menu.py переиспользует прежние оценки и квитанции callback, дополняя их причинами отказа и ручным просмотром статистики.
